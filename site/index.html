ComfyHarden

Read-only security evaluation for ComfyUI in production.

Generative tools now run on strong hardware, on company and studio networks. That is where they earn their keep, and where they need real security. ComfyHarden evaluates an existing instance and shows you exactly where it stands. The assessment changes nothing. The report it writes is what your coding agent uses to fix the problems.

Why now

Production changes the rules

ComfyUI is built to run locally and, by design, trusts anyone who can reach it. That is the right default on a laptop. On a network it means the operator owns security.

Comfy.org secures what it controls well: the registry scans and bans obfuscated nodes, and ComfyUI-Manager has security levels. ComfyHarden covers the other half, the deployment itself, which only you can see and configure. None of this is a knock on ComfyUI. It is simply what production readiness looks like for any high-powered tool on capable hardware.

The workflow

Assess, remediate, verify

ComfyHarden's assessment is read-only. Your coding agent does the fixing in between audit and verify, guided by the skills that ship with the tool.

comfyharden audit

Assess

A read-only scan across exposure, custom nodes, dependencies, model files, and host settings. It changes nothing and is safe to run on a live instance.

Output: a single A–F grade and the report
your coding agent

Remediate

Claude Code or any coding agent reads the report and applies the fixes under clear gates, guided by the shipped skills. ComfyHarden never touches the instance.

Output: a hardened instance, changed by the agent
comfyharden verify

Verify

Re-scans and diffs against the earlier report by fingerprint, so you can confirm each fix landed and nothing regressed. Read-only too.

Output: confirmation the findings cleared

Reversibility

Snapshot, detect drift, roll back

Capture a known-good state before anyone touches the instance. Later, see exactly what changed, and roll back if a change broke it or a scan shows tampering. The snapshot format supersets ComfyUI-Manager's own, so it stays restore-compatible.

comfyharden snapshot

Capture

One timestamped JSON of the full state: versions and commits, node hashes, dependencies, launch flags, and Manager config. Read-only.

Output: a baseline you can compare and restore to
comfyharden diff

Detect drift

Compare two states, or a baseline against live. A node file changed without its commit changing, a planted node, a config downgrade: the shape of a compromise. Also catches "what changed since it last worked."

Output: DRIFT findings, graded like any other
comfyharden restore

Roll back

Writes a rollback plan and script by default, changing nothing. The one command that can mutate the instance, only with --apply, and even then it never deletes, only quarantines.

Output: a reversible rollback to the baseline
Baseline

Eight best practices

The standard ComfyHarden measures against, and what a coding agent works from the report to apply. These matter most once an instance is reachable beyond a single local user.

01

Keep it on localhost

Do not expose it directly. Reach it through an authenticating, TLS-terminating proxy or a VPN.

02

Require authentication

Core has none, so it lives in the proxy or network. Multi-user mode is storage, not access control.

03

Stay current, set Manager to strong

Update core and Manager. On a network, disable runtime pip and git installs.

04

Vet custom nodes

Prefer verified publishers, read install scripts, avoid nodes that run code at import. Popularity is not trust.

05

Prefer safetensors

Treat .ckpt, .pt, and .bin from untrusted sources as code, not data. They can execute on load.

06

Run with least privilege

Non-root user or container. Never privileged, never the Docker socket, no broad host mounts.

07

Control secrets and egress

Keep secrets out of the environment every node can read. Restrict outbound network access.

08

Assess before you expose

Scan, fix, verify, and repeat on a schedule. Disable API nodes and metadata when not needed.

Output

A grade, a fix list, and an agent brief

One scan produces a plain human summary that leads with a single grade, plus machine-readable files and the agent skills. Point Claude Code or any coding agent at the fix list, and it works through the findings under clear gates.

report.md report.json report.sarif FIXES.md AGENTS.md

The grade is deterministic and explains itself. One confirmed "reachable without authentication" is enough for an F, whatever else is clean.

Roadmap

How it gets built

Each phase is useful on its own. Phase one alone covers most of the documented incident classes.

Phase 1

Assess

audit across the core areas, the threat feed, the report, and the agent skills.

Phase 2

Snapshot & verify

snapshot and diff with drift detection, verify, SARIF, the ML-BOM, and secrets and host checks.

Phase 3

Restore & freshness

restore (plan plus opt-in apply), signed feed updates, deeper node and secret scanning.

Phase 4

Continuous

A CI action, scheduled re-scans, and an optional local dashboard.
